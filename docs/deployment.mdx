# Deployment & Hosting

bAssistant is packaged as a pure static bundle without any Node or server-side runtime requirements.

## Build Commands

```bash
# Install dependencies
npm install

# Run development server
npm run dev

# Run hermetic test suite
npm run test

# Compile production bundle
npm run build
```

## Continuous Integration

The repository ships a GitHub Actions workflow at `.github/workflows/ci.yml`:

- **Triggers**: `push` and `pull_request` targeting `main` / `master`, plus manual `workflow_dispatch`.
- **Matrix**: Node.js `20.x` and `22.x` on `ubuntu-latest`.
- **Steps**: `actions/checkout` → `actions/setup-node` (npm cache) → `npm ci` → `npm test`
  (`vitest run`) → `npm run build` (`tsc && vite build`).

The workflow is a **test-and-build gate only** — it does not validate the docs site and does not deploy.
Anything that breaks `tsc`, the test suite, or the production build will fail CI.

## Deploying to Cloudflare Pages

bAssistant is a pure static SPA with no server runtime. Deployment is manual: build locally and upload
the `dist/` output (dashboard drag-and-drop or Wrangler).

- **Framework Preset**: None (or Vite)
- **Build Command**: `npm run build`
- **Build Output Directory**: `dist`
- **Root Directory**: `/`
- **Environment Variables**: None required

> **WASM path requirement:** the LiteParse engine loads its binary from the site root at
> `/liteparse_wasm_bg.wasm`. Because that file lives in `public/`, Vite copies it verbatim to the root
> of `dist/`, so it is served independently of the fingerprinted `dist/assets/` bundle. Any hosting
> setup must preserve this root path.

## `/api` Search Functions

Web search and academic search cannot be fetched directly from the browser (those hosts send no CORS
headers), so the app calls relative `/api/*` URLs. In production these are served by **Cloudflare Pages
Functions** in `functions/`:

| Route | File | Upstream |
| :--- | :--- | :--- |
| `/api/arxiv` | `functions/api/arxiv.ts` | `https://export.arxiv.org/api/query` (pass-through Atom XML) |
| `/api/websearch` | `functions/api/websearch.ts` | Keyless Tavily AI search (primary) with a DuckDuckGo HTML fallback, normalized via `src/lib/tavilySearch.ts` / `src/lib/ddgSearch.ts` |

`public/_routes.json` scopes Function invocation to `/api/*` (`{ "include": ["/api/*"], "exclude": [] }`),
so every other path remains a static asset:

```json
{ "version": 1, "include": ["/api/*"], "exclude": [] }
```

> **Deploy requirement:** because the app now ships Pages Functions, deploy through a **Pages project**
> (Wrangler `pages deploy`, or a Git-connected Pages build) so `/functions` is bundled — a plain static
> upload of `dist/` alone will 404 on `/api/*`. Locally, `npm run dev` does **not** run Functions; the
> `vite.config.ts` proxy/middleware serves the same routes, and `wrangler pages dev` exercises the real
> Functions.

In development there is no Pages runtime: `vite.config.ts` proxies `/api/arxiv` to `export.arxiv.org`
and mounts a `dev-search-endpoints` middleware for `/api/websearch`, so the same relative URLs work in
both environments. No `wrangler.toml`, `_redirects`, or `_headers` files are committed; SPA fallback
uses the Cloudflare Pages defaults.
